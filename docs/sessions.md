# Сессии анализа

Перед запуском обновите схему: `cd backend && uv run alembic upgrade head`.
Для анализа нужны загруженный справочник и настроенный поиск из [search.md](search.md).

- `POST /api/v1/sessions` без тела создаёт сессию (`draft`, ревизия 0).
- `POST /api/v1/sessions/{session_id}/messages` с `{"text": "Шкаф для одежды"}`
  сохраняет исходный текст и синхронно возвращает результат анализа новой ревизии.
  Текст должен содержать непробельные символы и быть не длиннее 4000 символов.
- `POST /api/v1/sessions/{session_id}/answers` с `{"question_id": "q2", "option_id": "o1"}`
  или `{"question_id": "q2", "unknown": true}` отвечает на `next_question` последней ревизии.
- `GET /api/v1/sessions/{session_id}` возвращает последний сохранённый снимок без поиска.

Все успешные ответы имеют HTTP 200 и контракт `SessionState` (также в `/api/docs`):
`session_id`, `revision`, `status`, `messages: [{id, text, created_at}]`,
`path: {category, group: {code, name}, positions} | null`, `alternatives`, `candidates`,
`candidate_counts: {in_group, compatible, excluded_by_rules}`, `facts`, `errors`, `warnings`,
`next_question`, `dialog`, `card_complete`, `missing_required`, `common_fields`, `unanswered`,
`unsupported_rules`. Идентификаторы сессии и сообщений — UUID4; время сообщения — ISO 8601 в UTC.

Поиск получает исходные сообщения и ответы об уточнении назначения в хронологическом
порядке. Из top-K берутся разные группы (`GROUP_TOP_K=5|10`, по умолчанию 10), дочерние
позиции и дубли не занимают отдельные места. Каждая группа обязательно проходит OpenJev
через существующий `DecisionBackend.choose`. Без `DECISION_URL` выбор группы завершается
`technical_error`; top-1 поиска и единственный потомок не дают права выбрать группу.

`group_checks[]` сохраняет код и название группы из каталога, типизированный
`verdict: supported|contradicted|not_stated`, относительные `scores`, независимые
`support_scores` (либо null, если адаптер их не поддерживает), `model_revision`,
`analysis_revision`, `criterion` и `role: group_template`. `criterion` — отправленные
инструкция и сведения каталога, а не сгенерированное объяснение: текущий адаптер не
возвращает текстовых оснований. Scores не являются калиброванной вероятностью соответствия.

Модель получает исходное описание без пересказа, актуальные уточнения, код и название,
категорию, ОКПД2, рубрики, обзор характеристик шаблона и конечных позиций. Повторяющиеся
значения объединяются; качественные поля идут первыми. На поле показываются до шести
значений, обзор ограничен 3000 символами с явной отметкой пропуска. Это проверка назначения,
точные ограничения всех позиций проверяются позже без сокращения справочника.

Правило зафиксировано в `domain/group_validation.py`: результат `supported` или
`contradicted` принимается только если модель выбрала этот ответ и обе его оценки
(относительная и независимая поддержка) не меньше 0.90. Иначе — `not_stated`.
Автоматически выбирается единственная подтверждённая группа, только когда все остальные
проверенные кандидаты противоречат назначению. После явного ответа на вопрос о назначении
достаточно подтверждения выбранной пользователем группы по тем же двум порогам: сам ответ
снимает неоднозначность между группами. Новое сообщение отменяет эту привязку и требует нового
выбора. Недостаток сведений не равен противоречию.
Это консервативное правило, не калибровка вероятности; замер и ограничения —
[проверка групп](../evals/reports/2026-10-10-group-validation.md).

При неоднозначности, пустой выдаче или отклонении всех top-K — `needs_clarification`,
`path: null`, пустые `candidates` и один вопрос `kind: purpose` о назначении.
Варианты — все неотклонённые проверенные группы, «Другое» и «Не знаю». Специфических
вопросов группы до её подтверждения нет. В данной реализации выбран предусмотренный
контрактом путь уточнения, без автоматического расширения поиска. Отклонение top-K
никогда не является основанием для `out_of_scope`.

Ответ с группой добавляет уточнение пользователя и заново запускает поиск и полную проверку;
это не принудительный выбор кода. «Другое» и «Не знаю» предлагают дописать назначение и не
повторяют тот же вопрос. Позднее сообщение с исправлением назначения запускает выбор заново.
Факты/ответы другой группы не переносятся: применяются только события истории своей группы,
исходные сообщения заново разбираются по схеме новой группы. Неполный ответ, неизвестные ID,
усечение или сбой модели дают `technical_error`; `recalculate` повторяет подбор даже без path.

В `alternatives` — до пяти проверенных групп: подтверждённые, затем неопределённые, затем
противоречащие; внутри статуса сохраняется retrieval-порядок. Выбранная группа исключена из
альтернатив. В API `path.group.role=group_template`, `candidates[].role=ktru_position`;
в UI — «Группа/шаблон» и «Позиция КТРУ». Все данные отображаются единым снимком ревизии;
фронтенд отклоняет запоздалые ответы. Ревизия проверки назначения сохраняется отдельно и
может быть старше ревизии правки характеристик, которая не меняет назначение.

Все конечные позиции подтверждённой группы возвращаются по коду, включая исключённые.
Группа без потомков сама становится единственной позицией, только после проверки назначения.

После поиска детерминированный экстрактор пересчитывает факты из всех сообщений в контексте
характеристик конечных позиций. Модель для извлечения не нужна. Парсер распознаёт десятичную
запятую и точку, диапазоны `100–120`, `100-120`, `от 100 до 120`, единицы длины, массы,
объёма и штук из `domain/units.py`. Число привязывается по слову-полю в трёх словах слева,
а качественное значение — по точному совпадению с каталогом (регистр и `ё/е` нормализуются).
Без надёжной привязки факт получает `ambiguous`. Единица не выводится из названия поля.
Размеры `80×60×75`, полуоткрытые диапазоны и отрицания не создают фактов, а дают `warnings`.
Одинаковые значения одного поля объединяются, включая эквивалентные единицы; разные значения
во всей истории помечаются `ambiguous` с предупреждением о противоречии.

`facts[]` содержит `id`, `field`, `characteristic_name | null`, `raw_value`, `raw_unit`,
`value`, `unit_code`, `kind: number|range|text|interval`, `normalization_rule`,
`origin: parser|user|catalog`, `status`, `source: {message_id, quote, start, end} | null`,
`bounds`. Статусы: `accepted_from_text`, `ambiguous`, `confirmed_by_user` (ответ на вопрос),
`derived_from_catalog` (единственное допустимое значение обязательного поля выбранной позиции),
`superseded` (замещён ответом пользователя по тому же полю: остаётся в истории, в проверках не
участвует). `interval` — ответ числовым значением каталога: `value` — его подпись, `bounds` —
значение каталога; совпадает, если целиком внутри допустимых значений позиции, частично —
`ambiguous`.
Координаты `[start, end)` — code points исходного сообщения. Числа в `value` — строки decimal,
диапазон — массив двух таких строк. ID факта строится из ID сообщения и координат цитаты.

`candidates[]` содержит `code`, `name`, `excluded`, `reason | null`, `matched_facts: [fact_id]`
и `checks: [{fact_id, result}]`. Результаты: `match`, `mismatch`, `unknown`, `ambiguous`,
`not_applicable`, `unsupported`. Проверка без конкретного факта имеет `fact_id: null`:
это отсутствие данных (`unknown`) или неподдержанное правило позиции (`unsupported`).
Единицы сравниваются по размерности и коду ОКЕИ, границы — точно, без допуска float.
Допустимость — объединение всех значений характеристики; частичное пересечение диапазонов
даёт `ambiguous`. Исключает только `mismatch` с фактом `accepted_from_text`.
Первое несовпадение даёт `reason: {fact_id, characteristic, allowed, given, text}`;
текст составляется из правил каталога и указанного значения, остальные проверки сохраняются.

Статусы: нет совместимых позиций — `conflict`; одна — `resolved` («Код определён»), даже при
неподдержанном правиле: оно попадает в `unsupported_rules: [{position, characteristic}]` как
предупреждение; несколько, и ни один ответ ни на один вопрос не меняет их множество —
`ambiguous_in_catalog` с `common_fields: [{characteristic, values}]` (поля с одинаковыми
допустимыми значениями у всех совместимых позиций); иначе `needs_clarification`.
`out_of_scope` — текст не описывает товар: группа не выбирается, `path` — `null`, кандидатов и
альтернатив нет, в `warnings` — просьба описать товар. Ближайшая группа векторного поиска есть
у любой строки, поэтому решают два шага: косинус с ней ниже `SEARCH_MIN_SIMILARITY` (0.45) —
сразу `out_of_scope`; выше — OpenJev (`DECISION_URL`) отвечает на вопрос `RELEVANCE`
(`usecase/sessions.py`), и `P(junk) ≥ 0.5` тоже даёт `out_of_scope`. Без `DECISION_URL` этот этап использует только порог; дальнейшая проверка назначения
без модели всё равно завершается технической ошибкой. Находка по коду КТРУ или проверенному синониму обе проверки пропускает. Сбой
OpenJev — `technical_error`. Проверяется весь текст сессии, как и в поиске. Замер —
[`2026-10-10-out-of-scope.md`](../evals/reports/2026-10-10-out-of-scope.md).
Отсутствие факта никогда не исключает позицию.
`card_complete` — код определён и `missing_required: [{characteristic, name}]` пуст;
незаполненные обязательные поля считаются для выбранной позиции, код характеристики — её.
`compatible + excluded_by_rules == in_group == len(candidates) == path.positions`. У пустой
сессии и технической ошибки путь отсутствует, счётчики нулевые.

`next_question: {question_id, kind: purpose|conflict|discriminate|required, characteristic, text,
options: [{id, label}], allow_unknown: true} | null` выбирается детерминированно
(`domain/dialog.py`, раздел 10.2 плана), по порядку:

1. `conflict` — поле с противоречивыми значениями из текста; варианты — эти значения.
2. `discriminate` — характеристика оставшихся позиций без принятого факта. Варианты — их
   допустимые значения как в каталоге: пересекающиеся интервалы не режутся, свободного ввода
   числа нет. Полезность — средняя по вариантам доля исключённых позиций минус 0.05 за каждый
   вариант сверх двух и 0.3 за повтор после «не знаю»; при равенстве — порядок характеристик в
   каталоге. Вопрос, любой ответ на который оставляет все позиции, не задаётся.
3. `required` — после кода: незаполненное обязательное поле выбранной позиции.

`question_id` уникален в ревизии. Ответ о характеристике — новая ревизия с полным пересчётом без поиска: группа
берётся из `path`, факты парсера — из всех сообщений, факты ответов — из `dialog: [{question_id,
kind, characteristic, revision, messages, option_id, fact, group}]`. Вариант даёт факт
`origin: user`, `status: confirmed_by_user`, который замещает факты по этому полю из сообщений до
ответа и конфликта не создаёт; неявное противоречие из более позднего сообщения требует разрешения. Ответы
по другой группе остаются в истории, но после смены группы поиском не применяются. «Не знаю» (`option_id: null`) факта не даёт; вопрос по этой характеристике
не задаётся, пока нет нового сообщения или ответа на другой вопрос, и после возвращается со
штрафом. Если различающие вопросы кончились из-за «не знаю» — `needs_clarification`,
`next_question: null`, такие характеристики в `unanswered`. «Не знаю» на обязательное поле
оставляет его в `missing_required`, статус не меняется.

Ответ на вопрос не из последней ревизии, в том числе повтор того же ответа, — 409
`stale_question` без новой ревизии; `Idempotency-Key` для ответов не нужен. Несуществующий
`option_id` или тело без ровно одного из `option_id` и `unknown: true` — 422.

Необязательный заголовок `Idempotency-Key` у отправки сообщения действует внутри сессии.
Тот же ключ и тот же исходный текст возвращают исходную ревизию, даже если уже появились новые.
Другой текст с тем же ключом даёт 409 `idempotency_conflict`.
Без ключа каждое сообщение создаёт ревизию. Неизвестная сессия — 404 `session_not_found`,
невалидный текст — 422.

Сбой модели, отсутствие её настройки или пустой справочник сохраняются как `technical_error`
с `errors: [{code, message}]`, исходным сообщением и новой ревизией, HTTP 200. Повтор по ключу
сохраняет этот результат; новое сообщение запускает поиск снова по всей истории.

Хранение — таблицы `analysis_sessions`, `session_messages`, `session_revisions`; каждая ревизия
содержит JSON-снимок; ревизия ответа строки в `session_messages` не добавляет. Отправка
сообщения и ответа одной транзакцией блокирует запись SQLite перед чтением последней ревизии и
проверкой ключа. Ограничения БД запрещают повтор номера ревизии
и ключа в сессии. Блокировка держится во время синхронного поиска, поэтому долгий поиск задерживает
остальные записи SQLite; это ограничение текущего синхронного каркаса.

Порт `SessionsRepository` реализован через SQLite и in-memory, `GroupSearcher` позволяет
подменять поиск в сценарных и HTTP-тестах. Проводка — `composition.build_usecases`.
Порт `FactExtractor.extract(messages, group)` получает `DeterministicFactExtractor` из
`main.py`; при сборке сессий он обязателен. Старый модельный контракт с `ExtractionRequest`
сохранён как `ModelFactExtractor`. Доменные типы — `domain/facts.py`, правила и объяснения —
`domain/rules.py`. Проверки без сети и моделей: `cd backend && uv run pytest`.

Числа каталога хранятся как `Decimal` в домене и как строки в SQLite, JSON-снимке и HTTP API
каталога (`concrete`, `min`, `max`). Миграция сохраняет старые REAL в доступной им точности;
чтобы восстановить исходные цифры XML после обновления старой базы, повторите синхронизацию
каталога по команде из README. Новые загрузки не проходят через float.

## Сопоставление свободных enum-значений

`DECISION_URL` подключает OpenJev в `main.production_usecases`; без URL остаётся режим парсера.
`composition.build_usecases(decision=...)` принимает любой `DecisionBackend` и оборачивает его
общей проверкой из `model_checks`. Таймаут (`DECISION_TIMEOUT`, секунды), исключение, неверный
состав ответов, усечение и невалидные вероятности сохраняют сообщение в новой ревизии
`technical_error`. Подтверждения пользователя сохраняются в `enum_resolutions` даже при сбое.

При подключённой decision-модели качественные поля со списками значений обрабатываются
`EnumMapper`, числовые — прежним парсером. Непроверенные явные enum-значения парсера
сохраняются для диагностики опечаток и отсутствия в каталоге; они не исключают позиции.
Подтверждение предложения по тому же полю замещает эту гипотезу. Это не позволяет точному парсеру принять одну часть
неоднозначного или многозначного описания раньше проверки. Сначала числовые и подтверждённые
пользователем факты сужают группу; вопросы строятся по характеристикам оставшихся позиций.
Характеристики с одинаковым нормализованным именем объединяются независимо от локальных кодов;
допустимые значения и правила множественности объединяются без повторов. Произвольные разные
имена не признаются синонимами без словаря. Набор вариантов одного поля не дублируется по
позициям. Для одного сообщения порт получает пакет вопросов и пакет утверждений.

Одиночный выбор включает «не указано». Утверждения проверяются для каждого допустимого
значения, в том числе при одиночном выборе: так второе указанное значение не теряется из-за
`choose`. Множественный выбор использует только `verify`. HTTP-адаптер переводит пакет вопросов
в отдельные `/v1/choice` существующего сервиса, а NLI делит на пакеты до 32 утверждений.
Ответ с «не указано» не создаёт модельного факта и ошибки. Предложение хранит в `facts`:

- `origin: decision`, `status: proposed`, нормализованное `value`;
- `source` с исходным сообщением и его точными координатами, `raw_value` с цитатой;
- `normalization_rule: enum_decision_v2`, `model_revision`, `model_score` (сырая оценка для
  аудита и калибровки, не вероятность правильности; UI её не показывает).

`proposed` не исключает позиции и не заполняет обязательное поле автоматически из каталога.
`enum_proposals` содержит `id`, `characteristic`, `suggested`, `options`, `selections`
(`values`, `multiple` для каждого допустимого набора) и `reason`. UI различает предложение,
автоматически принятое значение и подтверждение пользователя. Конкретные предложения имеют
действия «Принять», «Выбрать другое», «Не знаю».

```http
POST /api/v1/sessions/{session_id}/enum-resolutions
Content-Type: application/json

{"expected_revision": 1, "proposal_id": "enum:1:0", "action": "accept"}
```

`action: choose` дополнительно требует непустой массив различных `values` из `options`.
Несколько значений допустимы, только если хотя бы одна схема разрешает их **совместно**.
`accept` использует `suggested` с той же проверкой; недопустимое сочетание требует выбора
пользователя. После принятия несколько значений исключают позиции с одиночным выбором,
даже если каждое из значений отдельно входит в их список. `action: unknown` факта не создаёт,
поле остаётся незаполненным, повторный вопрос откладывается до смены контекста.

Успех возвращает `SessionState` новой ревизии. Неверные значения/множественность — 422,
неверный `expected_revision` или неактуальное предложение — 409 `stale_revision`, сессия не
изменяется. Проверка и запись выполняются под той же SQLite-блокировкой, что ответы диалога.
Клиент при 409 перечитывает сессию, сохраняя черновик. Принятие сохраняет происхождение модели и
цитату с `status: confirmed_by_user`; выбор другого значения даёт `origin: user`.

`enum_resolutions` хранит предложение, поле, группу, ревизию, число сообщений и принятые факты;
пустые `facts` означают «не знаю». Новое сообщение не отменяет подтверждение по тому же полю;
новый явный ответ диалога может его заменить. Подтверждения другой группы сохраняются, но не
участвуют в текущем расчёте. Принятие и выбор пересчитывают правила без нового вызова модели.
Снимки старого формата читаются с пустыми `enum_proposals`/`enum_resolutions`.

Автопринятие в production **включено с порогом 0,90** для ревизии
`a20448012c213128955ca0c693e7c943865cab77`. Настройки: `DECISION_AUTO_ACCEPT_ENABLED`
(по умолчанию `true`), `DECISION_AUTO_ACCEPT_THRESHOLD` (`0.90`), `DECISION_REVISION`.
`false` оставляет все конкретные предложения на подтверждение. Общая проводка для тестов
и других точек сборки по умолчанию использует выключенный `AutoAcceptance`.

Принятое моделью значение получает `accepted_from_model`. Проверяется не только оценка:
сочетание должно допускаться каталогом, ревизия модели совпадать с настроенной, а значение
однозначно связываться с полем. В одном фрагменте должно быть явно названо поле/его
содержательное слово либо лексически близкое значение только одного поля. Упоминание другой
части товара блокирует автопринятие даже при высокой оценке. Словоформы и части определяются
консервативной лексической эвристикой; её ограничения измеряются вместе с качеством модели.
Несколько сообщений требуют подтверждения, чтобы не принять устаревшее значение до обработки
исправления. Уже подтверждённые пользователем значения остаются принятыми.

При наличии `не`, `без`, `нет` в сообщении положительные модельные факты из него не создаются.
Это снижает полноту, в том числе у смешанных сообщений с положительными фактами. Порог 0,90 —
продуктовый компромисс в пользу частоты автопринятия, не гарантия 90% или 99% правильности.
Абсолютные числа, неопределённость и новая независимая от настройки проверка —
[отчёт](../evals/reports/2026-10-10-enum-mapping.md).

## Диагностика характеристик

`errors` содержит различимые формы: техническое `{code, message}` или диагностику с `kind`:
`typo`, `value_not_in_catalog`, `out_of_range`. `synonym` находится только в отдельном
`normalizations`. `warnings` по-прежнему описывает неполноту. Старые снимки без
`normalizations` читаются с пустым массивом. Диагностики сохраняются в ревизии и возвращаются
при повторном чтении/идемпотентном запросе.

У диагностики есть nullable `fact_id`, `source_quote`, `source` (`message_id`, `quote`,
`start`, `end` — полуинтервал в Unicode code points), `expected`, nullable `suggestion`,
`candidates`, `rule_ref` (позиция, код/имя характеристики и коды значений), `scope`
(группа, проверенные позиции, полнота), `requires_confirmation`, `explanation` и
nullable `alias_source`. Несколько близких вариантов возвращаются вместе; единственный
вариант попадает в `suggestion`. Числовые объяснения содержат границы, включённость и единицы
из КТРУ. Проверка использует всю группу, включая исключённые позиции, а не текущих кандидатов.

Явные пары `Название характеристики: значение` после начала строки, точки или `;` позволяют
проверить неизвестные enum и числовые поля. Неизвестные enum остаются непринятыми гипотезами.
Неясное поле, отрицание, неподдержанное или отсутствующее правило хотя бы одной позиции и
шаблон без конечных позиций не доказывают отсутствие значения. При точном совпадении
групповая ошибка отсутствует. Далее проверяется контекстный словарь, затем полное сравнение
enum по Damerau–Левенштейну: длина ≤3 — только точное, 4–7 — до одной правки, ≥8 — до двух и
не более 25%; длина равна максимуму длин. Ближайшие варианты не ограничивают scope проверки.

Проверенные синонимы привязаны к компоненту и источнику выгрузки в
`backend/app/adapter/value_aliases.py`. Они показываются как нормализация, не как ошибка;
перенос между компонентами не допускается. Синонимы и исправления не создают подтверждённый
факт, а предложения соседней единицы мм/см/м не меняют исходную единицу.

`SPELLING_URL` — URL OpenAI-совместимого Qwen с `/v1`, `SPELLING_MODEL` — имя модели,
`SPELLING_API_KEY` — необязательный ключ. Примеры — `backend/.env.example`. Проход вызывается
только для нового сообщения, не при чтении, повторе ключа или ответе на вопрос. Сервис
возвращает гипотезы; приложение проверяет точность цитаты, границы и защищённые значения.
Без привязки к характеристике `fact_id = null`, `rule_ref = []`, `scope.complete = false`:
это орфографическая гипотеза, а не нарушение КТРУ. Числа, единицы, артикулы и регистровые
названия не исправляются. Технические `spelling_failed` / `spelling_invalid_response`
обозначают неполную проверку и не переводят успешный детерминированный анализ в
`technical_error`. Без настроенного сервиса проверка орфографии явно недоступна.

Экран поставщика выделяет цитаты в истории сообщений и показывает объяснения, варианты и
ссылки на правила в области «Следующее действие». Принятие исправлений — отдельный сценарий.

## Правка, удаление и восстановление фактов

`PATCH /api/v1/sessions/{id}/facts/{fact_id}` принимает `expected_revision` текущей сессии
и `action`: `edit`, `confirm`, `delete`, `restore`, `split`, `accept_suggestion`.
Это тот же контракт ревизии, что у `enum-resolutions`; ответы диалога защищены `question_id`.
Все операции проверяют ревизию под блокировкой записи. Устаревание — HTTP 409
`stale_revision`, без изменения фактов, истории и номера ревизии. Неизвестный или уже
изменённый факт — 404 `fact_not_found`, невалидная правка — 422 `invalid_fact_edit`.

Пример замены ширины:

```json
{
  "expected_revision": 2,
  "action": "edit",
  "characteristic_name": "Ширина",
  "component": "столешница",
  "raw_value": "1000",
  "raw_unit": "мм",
  "kind": "number"
}
```

Характеристика выбирается из `editable_fields` текущей группы. `kind` — `text`, `number`
или `range`; диапазон вводится как `900..1100`, десятичная запятая допустима.
Для смены привязки существующего интервала каталога используется `kind: interval` с
неизменными `raw_value`/`raw_unit`: точные границы и их включённость сохраняются.
Для нового числового значения пользователь выбирает `number` или `range`. Единица —
поддержанный символ или код ОКЕИ. Можно менять значение, единицу, характеристику и часть
товара одновременно. Ручное значение вне enum сохраняется как утверждение пользователя,
проходит правила и получает диагностику; справочник не изменяется. Для диагностики ручного
ввода `source.message_id` имеет вид `fact:<id>`: такая цитата не подсвечивается в сообщениях.
Исходный источник заменяемого факта остаётся в истории.

Замена создаёт новый ID; старый факт получает `superseded` и `superseded_by`. Удаление
оставляет `deleted`, выключая ограничение. Повторное извлечение старых сообщений не отменяет
эти действия. Новое сообщение может заново утверждать характеристику. Удалённое значение,
выведенное из каталога, не заполняется снова автоматически: обязательное поле остаётся в
`missing_required`, единственное допустимое значение можно подтвердить ответом на вопрос.

`fact_history` хранит действие, ревизию, время UTC, группу, снимки `before`/`after` с
происхождением, единицами и привязкой. `before` содержит исторические факты уже с отметкой
замещения/удаления. `restore` создаёт новую запись и новый факт; `restored_from` указывает
восстановленный ID. Восстановление замещает актуальный конец цепочки, в том числе после
смены характеристики/компонента. История не стирается. Подтверждения из диалога и
`enum-resolutions` используют тот же механизм записи истории; «Не знаю» факта не создаёт.
Старые JSON-снимки читаются с пустой историей, миграция таблиц не нужна.

Неявное противоречие одному полю/компоненту, включая подтверждённый ответ, даёт `conflict` и
вопрос. Спорные значения имеют `ambiguous` и не исключают позиции. Разные части товара
и допустимое множество значений не считаются конфликтом; правила множественности каждой
позиции проверяются отдельно. Эквивалентные величины в разных единицах не конфликтуют.

В редакторе можно оставить одно значение (`confirm` с `related_ids` остальных утверждений),
ввести другое (`edit` с `related_ids`), удалить все спорные (`delete` с `related_ids`) или
разделить их по частям (`split`: основной факт, `related_ids`, массив `bindings` с явной
привязкой каждого значения). Сначала идёт основной факт, затем связанные факты в порядке
снимка. Для текстовых исправлений поддержаны конструкции «исправь ширину на 100 см» и
«нет, не деревянный, металлический», если парсер однозначно распознал новое значение и
единственный заменяемый факт. Неоднозначное исправление сохраняется как запрос уточнения
с `normalization_rule: correction_needs_binding`; его нужно привязать в редакторе.
Общее понимание свободных формулировок эта эвристика не обеспечивает.

### Принятие диагностических предложений

Для `accept_suggestion` передаются `diagnostic_index` (индекс среди диагностик из `errors`,
затем `normalizations`), ревизия и явные поля привязки/значения. Значение проверяется против
предложения этой ревизии. При `fact_id: null` используется `POST /api/v1/sessions/{id}/facts`
с тем же телом: характеристику пользователь задаёт явно. UI показывает редактируемую часть
товара и отдельное подтверждение. Гипотеза единицы до подтверждения не меняет исходный факт.
Предложение другой ревизии не применяется; его нужно открыть заново. Модельные предложения
сохраняют существующий endpoint `enum-resolutions` и ограниченный каталогом выбор.

### Пересчёт, возвращённые позиции и сбои

Правка пересчитывает всю выбранную группу, включая исключённые позиции. Новое описание
повторяет поиск группы; позиции из впервые найденной группы не отмечаются возвращёнными.
У ранее исключённой позиции, ставшей совместимой, появляется `returned_reason`. Она сохраняется
в снимке и при GET/обновлении страницы. Следующая правка заново вычисляет отметки.

При сбое порта анализа правка и история сохраняются: `status: technical_error`,
`results_stale: true`, `card_complete: false`, старые кандидаты не считаются актуальным
подтверждением кода. `analysis_revision` указывает ревизию последнего успешного анализа.
`POST /api/v1/sessions/{id}/recalculate` с `expected_revision` повторяет расчёт без нового
сообщения и без новой записи истории. Успех обновляет `analysis_revision` и снимает
`results_stale`.

При конфликте ревизий редактор сохраняет несохранённый ввод, показывает текущие значения и
требует явного сравнения перед повторным применением. Автоматического повтора нет. Для
устаревших предложений и группового разрешения конфликтов требуется открыть актуальное
действие заново.

Проверки выполняются через HTTP на временной SQLite и локальных заглушках:
`cd backend && uv run pytest tests/test_fact_edits.py tests/test_enum_sessions.py`.
UI: `cd frontend && npm test`, ручная проверка клавиатуры и ширины 390 px;
снимки — `docs/screenshots/fact-editing-desktop.jpg`, `fact-editing-mobile.jpg`.
