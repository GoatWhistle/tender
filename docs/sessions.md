# Сессии анализа

Перед запуском обновите схему: `cd backend && uv run alembic upgrade head`.
Для анализа нужны загруженный справочник и настроенный поиск из [search.md](search.md).

- `POST /api/v1/sessions` без тела создаёт сессию (`draft`, ревизия 0).
- `POST /api/v1/sessions/{session_id}/messages` с `{"text": "Шкаф для одежды"}`
  сохраняет исходный текст и синхронно возвращает результат анализа новой ревизии.
  Текст должен содержать непробельные символы и быть не длиннее 4000 символов.
- `GET /api/v1/sessions/{session_id}` возвращает последний сохранённый снимок без поиска.

Все успешные ответы имеют HTTP 200 и контракт `SessionState` (также в `/api/docs`):
`session_id`, `revision`, `status`, `messages: [{id, text, created_at}]`,
`path: {category, group: {code, name}, positions} | null`, `alternatives`, `candidates`,
`candidate_counts: {in_group, compatible, excluded_by_rules}`, `facts`, `errors`, `warnings`,
`next_question`. Идентификаторы сессии и сообщений — UUID4; время сообщения — ISO 8601 в UTC.

Поиск получает все исходные сообщения по порядку, склеенные переводом строки, без фильтра
категории. Первая группа становится выбранной; следующие четыре — альтернативами с кодом,
названием, категорией, скором и `methods` с вкладами lexical/vector/synonym.
Все конечные позиции выбранной группы возвращаются по коду, включая исключённые.
Группа без потомков сама становится единственной позицией.

После поиска детерминированный экстрактор пересчитывает факты из всех сообщений в контексте
характеристик конечных позиций. Модель для извлечения не нужна. Парсер распознаёт десятичную
запятую и точку, диапазоны `100–120`, `100-120`, `от 100 до 120`, единицы длины, массы,
объёма и штук из `domain/units.py`. Число привязывается по слову-полю в трёх словах слева,
а качественное значение — по точному совпадению с каталогом (регистр и `ё/е` нормализуются).
Без надёжной привязки факт получает `ambiguous`. Единица не выводится из названия поля.
Размеры `80×60×75`, полуоткрытые диапазоны и отрицания не создают фактов, а дают `warnings`.
Одинаковые значения одного поля объединяются, включая эквивалентные единицы; разные значения
во всей истории помечаются `ambiguous` с предупреждением о противоречии.

`facts[]` содержит `id`, `field`, `characteristic_name | null`, `raw_value`, `raw_unit`,
`value`, `unit_code`, `kind: number|range|text`, `normalization_rule`, `origin: parser`,
`status: accepted_from_text|ambiguous`, `source: {message_id, quote, start, end}`.
Координаты `[start, end)` — code points исходного сообщения. Числа в `value` — строки decimal,
диапазон — массив двух таких строк. ID факта строится из ID сообщения и координат цитаты.

`candidates[]` содержит `code`, `name`, `excluded`, `reason | null`, `matched_facts: [fact_id]`
и `checks: [{fact_id, result}]`. Результаты: `match`, `mismatch`, `unknown`, `ambiguous`,
`not_applicable`, `unsupported`. Проверка без конкретного факта имеет `fact_id: null`:
это отсутствие данных (`unknown`) или неподдержанное правило позиции (`unsupported`).
Единицы сравниваются по размерности и коду ОКЕИ, границы — точно, без допуска float.
Допустимость — объединение всех значений характеристики; частичное пересечение диапазонов
даёт `ambiguous`. Исключает только `mismatch` с фактом `accepted_from_text`.
Первое несовпадение даёт `reason: {fact_id, characteristic, allowed, given, text}`;
текст составляется из правил каталога и указанного значения, остальные проверки сохраняются.

Нет совместимых позиций — `conflict`; одна совместимая без неподдержанных правил — `resolved`;
иначе `needs_clarification`. Отсутствие факта никогда не исключает позицию. `resolved`
означает единственную совместимую позицию, но не наличие фактов для всех её характеристик.
`next_question: null`; `compatible + excluded_by_rules == in_group == len(candidates)
== path.positions`. У пустой сессии и технической ошибки путь отсутствует, счётчики нулевые.

Необязательный заголовок `Idempotency-Key` у отправки сообщения действует внутри сессии.
Тот же ключ и тот же исходный текст возвращают исходную ревизию, даже если уже появились новые.
Другой текст с тем же ключом даёт 409 `idempotency_conflict`.
Без ключа каждое сообщение создаёт ревизию. Неизвестная сессия — 404 `session_not_found`,
невалидный текст — 422.

Сбой модели, отсутствие её настройки или пустой справочник сохраняются как `technical_error`
с `errors: [{code, message}]`, исходным сообщением и новой ревизией, HTTP 200. Повтор по ключу
сохраняет этот результат; новое сообщение запускает поиск снова по всей истории.
`out_of_scope` и `ambiguous_in_catalog` зарезервированы, но пока не выставляются.

Хранение — таблицы `analysis_sessions`, `session_messages`, `session_revisions`; каждая ревизия
содержит JSON-снимок. Отправка сообщения одной транзакцией блокирует запись SQLite перед
чтением последней ревизии и проверкой ключа. Ограничения БД запрещают повтор номера ревизии
и ключа в сессии. Блокировка держится во время синхронного поиска, поэтому долгий поиск задерживает
остальные записи SQLite; это ограничение текущего синхронного каркаса.

Порт `SessionsRepository` реализован через SQLite и in-memory, `GroupSearcher` позволяет
подменять поиск в сценарных и HTTP-тестах. Проводка — `composition.build_usecases`.
Порт `FactExtractor.extract(messages, group)` получает `DeterministicFactExtractor` из
`main.py`; при сборке сессий он обязателен. Старый модельный контракт с `ExtractionRequest`
сохранён как `ModelFactExtractor`. Доменные типы — `domain/facts.py`, правила и объяснения —
`domain/rules.py`. Проверки без сети и моделей: `cd backend && uv run pytest`.

Числа каталога хранятся как `Decimal` в домене и как строки в SQLite, JSON-снимке и HTTP API
каталога (`concrete`, `min`, `max`). Миграция сохраняет старые REAL в доступной им точности;
чтобы восстановить исходные цифры XML после обновления старой базы, повторите синхронизацию
каталога по команде из README. Новые загрузки не проходят через float.
