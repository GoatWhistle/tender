# Сессии анализа

Перед запуском обновите схему: `cd backend && uv run alembic upgrade head`.
Для анализа нужны загруженный справочник и настроенный поиск из [search.md](search.md).

- `POST /api/v1/sessions` без тела создаёт сессию (`draft`, ревизия 0).
- `POST /api/v1/sessions/{session_id}/messages` с `{"text": "Шкаф для одежды"}`
  сохраняет исходный текст и синхронно возвращает результат анализа новой ревизии.
  Текст должен содержать непробельные символы и быть не длиннее 4000 символов.
- `GET /api/v1/sessions/{session_id}` возвращает последний сохранённый снимок без поиска.

Все успешные ответы имеют HTTP 200 и контракт `SessionState` (также в `/api/docs`):
`session_id`, `revision`, `status`, `messages: [{id, text, created_at}]`,
`path: {category, group: {code, name}, positions} | null`, `alternatives`, `candidates`,
`candidate_counts: {in_group, compatible, excluded_by_rules}`, `facts`, `errors`, `warnings`,
`next_question`. Идентификаторы — UUID4; время сообщения — ISO 8601 в UTC.

Поиск получает все исходные сообщения по порядку, склеенные переводом строки, без фильтра
категории. Первая группа становится выбранной; следующие четыре — альтернативами с кодом,
названием, категорией, скором и `methods` с вкладами lexical/vector/synonym.
Все конечные позиции выбранной группы возвращаются по коду с `excluded: false`.
Группа без потомков сама становится единственной позицией.

Более одной позиции дают `needs_clarification`, одна — `resolved`. Пока фактов и правил нет,
`facts` пуст, `next_question: null`, `compatible == in_group == len(candidates) == path.positions`,
`excluded_by_rules == 0`. У пустой сессии и технической ошибки путь отсутствует, счётчики нулевые.
`resolved` на этом этапе означает единственную конечную позицию, а не проверенные характеристики.

Необязательный заголовок `Idempotency-Key` у отправки сообщения действует внутри сессии.
Тот же ключ и тот же исходный текст возвращают исходную ревизию, даже если уже появились новые.
Другой текст с тем же ключом даёт 409 `idempotency_conflict`.
Без ключа каждое сообщение создаёт ревизию. Неизвестная сессия — 404 `session_not_found`,
невалидный текст — 422.

Сбой модели, отсутствие её настройки или пустой справочник сохраняются как `technical_error`
с `errors: [{code, message}]`, исходным сообщением и новой ревизией, HTTP 200. Повтор по ключу
сохраняет этот результат; новое сообщение запускает поиск снова по всей истории.
`out_of_scope`, `ambiguous_in_catalog` и `conflict` зарезервированы, но пока не выставляются.

Хранение — таблицы `analysis_sessions`, `session_messages`, `session_revisions`; каждая ревизия
содержит JSON-снимок. Отправка сообщения одной транзакцией блокирует запись SQLite перед
чтением последней ревизии и проверкой ключа. Ограничения БД запрещают повтор номера ревизии
и ключа в сессии. Блокировка держится во время синхронного поиска, поэтому долгий поиск задерживает
остальные записи SQLite; это ограничение текущего синхронного каркаса.

Порт `SessionsRepository` реализован через SQLite и in-memory, `GroupSearcher` позволяет
подменять поиск в сценарных и HTTP-тестах. Проводка — `composition.build_usecases`.
Проверки без сети и моделей: `cd backend && uv run pytest tests/test_sessions.py`.
