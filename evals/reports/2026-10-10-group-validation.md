# Проверка назначения групп КТРУ

## Методика

Продуктовые `POST /api/v1/search` и `POST /api/v1/sessions/{id}/messages`, реальные
OpenJev-4B-v5 и Qwen3-Embedding-0.6B, временная копия `artifacts/ktru-search.sqlite3`.
Один и тот же [размеченный набор](../groups/cases.json): восемь положительных описаний
столов, одно без назначения, одно вне имеющегося каталога. Для программистов/офисной работы
допустимы письменная и компьютерная группы; hit@K — хотя бы одна допустимая группа.
Производственный шаблон — `31.02.10.000-00000005`; конечная позиция — отдельный код.

Порог 0.90 зафиксирован до вызовов модели, по результатам этого набора не изменялся.
Для автоматического выбора без ответа пользователя требуются оба score ≥ 0.90 у одной
подтверждённой группы и противоречие у остальных. Отсутствие информации — отдельный результат.
После явного выбора назначения пользователь снимает неоднозначность; выбранная группа всё
равно должна заново получить оба score ≥ 0.90. Относительные choice scores и независимая
поддержка критериев сохраняются раздельно. Ни те ни другие не объявляются калиброванной
вероятностью пригодности товара.

Набор создан для этой регрессии вручную, это маленькая контрольная выборка, а не доказательство
качества на всём каталоге. Нет train/dev-подбора порогов; отдельная независимая калибровка
не проводилась. K=5 запускается перед K=10; серверный кеш не сбрасывался, GPU общий.
Задержка — полная обработка сообщения с retrieval и всеми проверками. Дополнительный
запрос поиска для метрики сделан до таймера. Цифры не являются нагрузочным benchmark. Опциональная орфография отключена;
предупреждения `spelling_failed` сохраняются, но не считаются отказами проверки группы.

## Результат

| K | Retrieval hit@K | Ошибочные автовыборы | Уточнения | Технические сбои | Средняя задержка |
|---|---|---|---|---|---|
| 5 | 8/8 | 0/10 | 10/10 | 0 | 6.35 с |
| 10 | 8/8 | 0/10 | 10/10 | 0 | 8.96 с |

Ошибок retrieval среди восьми положительных кейсов нет. Для «рабочий стол программистам»
поиск действительно ставит производственный стол первым; компьютерный — четвёртым,
письменный — шестым (только K=10). Производственная группа не выбрана, специфического
вопроса «Вид: Разделочный/Кондитерский» нет. Возвращается вопрос о назначении.

Ошибочных автоматических выборов после Jev нет, но **автоматических выборов вообще нет**:
все 10 первичных описаний требуют уточнения. Включая шесть положительных кейсов с одной
размеченной группой. Это ограничение консервативного решения, а не 100% семантическая точность.
Scores OpenJev часто не достигают порога либо оставляют неподтверждённые альтернативы.
Увеличение K в этом наборе добавляет альтернативы и задержку, но не улучшает hit@K.
Отклонение/неопределённость top-K не переводит хирургический стол в `out_of_scope`.

Первый диагностический прогон выявил HTTP 413 на полном JSON характеристик лабораторного
стола. Представление заменено компактным обзором каталога; итоговый прогон выше не имеет
этой ошибки. Пороги при исправлении не менялись. Сырые итоговые ответы и SHA256 базы/набора —
[JSON](2026-10-10-group-validation.json). Ревизия OpenJev:
`a20448012c213128955ca0c693e7c943865cab77`.

## Воспроизведение

```bash
backend/.venv/bin/python evals/groups/run.py --output var/group-validation.json
cd backend
uv run pytest tests/test_group_validation.py tests/test_openjev_http.py
```

Интеграционные ответы-заглушки отдельно проверяют K=5/10, отсутствие/неполноту/сбой модели,
низкую абсолютную поддержку при относительном score=1, повтор расчёта, исправление назначения,
явный выбор пользователя, «Другое»/«Не знаю», пустую выдачу, дубли и дочерние позиции.
Это проверки управления состоянием; семантическое качество подтверждают только реальные
данные выше, с указанными ограничениями.

## Проверка интерфейса и продолжения диалога

В браузере на реальных сервисах: «рабочий стол программистам» → уточнение назначения →
ответ «Стол компьютерный» → повторная проверка всех десяти групп. Исходное описание
сохранено. Код не выбран: для компьютерной группы независимая поддержка 0.9913,
относительный score 0.8198, ниже фиксированного порога. Это ещё одно ограничение текущего
правила: даже явное уточнение не гарантирует завершения диалога. Пороги не снижались ради
прохождения этого кейса. [Полные снимки двух ревизий](2026-10-10-group-purpose-dialog.json).

Ошибок JavaScript в этом сценарии нет. Скриншоты актуальных снимков после завершения анимации: [desktop](../../docs/screenshots/group-purpose-desktop.png),
[390 px](../../docs/screenshots/group-purpose-mobile.png),
[после ответа](../../docs/screenshots/group-purpose-answer.png).

После добавления нового словаря и extractor из main (`7110d05`) тот же набор прогнан
повторно без изменений порогов. Это регрессия, не новый независимый holdout. Исходный
отчёт выше сохранён. [Повторные сырые ответы и SHA256 обновлённой базы](2026-10-10-group-validation-after-main.json).
